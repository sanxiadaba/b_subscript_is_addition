# a[i] 凭什么能写成 i[a]？——C 的下标从来就不是数组语法

## 结论先说

C 的下标**不是数组语法**，它是一个运算符，定义在 C11 §6.5.2.1：

```text
E1[E2]  ≡  *((E1) + (E2))
```

两边**完全对称**。所以 `a[i]` 和 `i[a]` 不是两种写法，是**同一个表达式的同一次加法**——
编译器对它们生成的指令**逐字节相同**。

这里有一个大多数人不知道的前提（同一条款）：`E1` 与 `E2` 里**必须恰好有一个是指针、
另一个是整数**。两个整数相加再解引用不是合法程序；`"hello"[1]` 能成立，是因为
字符串字面量在这个语境下退化成 `char *`。

## 三个关键实测

### 1. 九种写法，一个答案

```text
A1 arr[2] = 30        A2 2[arr] = 30        A3 p[2] = 30
A4 2[p] = 30          A5 *(p+2) = 30        A6 (2+p)[0] = 30
A7 (p+2)[0] = 30      A8 "hello"[1] = 101   A9 1["hello"] = 101
```

`gcc -Wall -Wextra` 对这九行报 **0 个警告**（`OUTPUT.txt` 的 `compiler: ZERO warnings, exit 0`）。

> ⚠️ 上面那张表里的 `101` 是**字符 `'e'` 的编码**，而 `docs/measured.md` 里那一行
> 打出来的是 **`e`**（`printf` 用的是 `%c`）。两个数说的是同一件事 ——
> 这里写编码是因为它同时说明了一件事：**`"hello"[1]` 的类型是 `char`**，
> 而 `arr[2]` 的类型是 `int`（见下面第 4 条）。

### 2. 反汇编：`q[i]` 与 `i[q]` 编出来的指令**逐字相同**

`objdump -d` 的真产物（`-O2 -m32`）：

```text
-- get_i --                    -- get_commuted --
  8b 54 24 08   mov 0x8(%esp),%edx      8b 54 24 08   mov 0x8(%esp),%edx
  8b 44 24 04   mov 0x4(%esp),%eax      8b 44 24 04   mov 0x4(%esp),%eax
  8b 04 90      mov (%eax,%edx,4),%eax  8b 04 90      mov (%eax,%edx,4),%eax
```

**机器码字节也逐字相同**（`8b 54 24 08` / `8b 44 24 04` / `8b 04 90`）。

`(%eax,%edx,4)` 就是「基址 + 下标 × 4」——**那个 4 是 `sizeof(int)`**。
第三组换成 `char`，它变成 **1**：

```text
-- get_char --
  0f be 04 02   movsbl (%edx,%eax,1),%eax
```

`movsbl` 而不是 `mov`，是因为 `char` 要**符号扩展**到 `int` 才能返回。
两处差异（缩放 4→1、`mov`→`movsbl`）**都来自元素类型**，与方括号写在哪边无关。

### 3. 数组名在加法里会退化成指针

```text
B1 sizeof(arr) = 20              数组本身：5 个 int
B2 sizeof(p) = 4                 传进函数的指针：一个地址
B4 sizeof(arr) / sizeof(p) = 5
B5 sizeof(arr) / sizeof(*arr) = 5
```

⚠️ `B4` 与 `B5` 在 i686 上**巧合相等**（指针 4 字节 = `int` 4 字节），
在 x64 上 `B4` 会得 **2**。所以那个「数出元素个数」的惯用写法必须用 `*arr` 而不是 `p`
——**代码里对，理由常常是错的**。

## 它也会失效

这一期讲的不是"随便写都行"。`E1[E2]` 的等价**只在这几条同时成立时**才对：

| 前提 | 不成立时 |
|---|---|
| 恰好一侧是指针、另一侧是整数 | `1[2]` 不是合法程序（两个整数） |
| 指针指向**足够长**的数组，下标在界内 | **越界不检查**：`arr[7]` 照样编译、照样跑，读到的是别的内存（见 `d_bounds.c` / `e_bounds.c`） |
| 那个"加法"是**指针加法**（按元素大小缩放） | 数组名一旦**退化**成指针，`sizeof` 就量不到数组了（见上面第 3 条） |
| 一侧是数组名时它确实退化了 | 除了 `sizeof` / `&` / 字符串字面量初始化之外，数组名在表达式里都会退化 |

**最容易踩的一条**：`sizeof` 是那少数几个**不让数组名退化**的语境之一——
所以 `sizeof(arr)` 是 20，而同一个 `arr` 传进函数之后 `sizeof` 只剩 4。
这不是编译器的怪癖，是"数组和指针分家"这件事的直接后果。

**还有一条**：越界的**警告方式不一样**。下标落在真正的数组上时 gcc 会警告
（`array subscript is below array bounds`，见 `OUTPUT.txt` 的 `WARN:` 行）；
而下标落在**指针**上时**一声不响**（同一份输出里 `compiler: ZERO warnings, exit 0`）。
⇒ "编译器会帮我看着"这个想法，只对数组名成立。

## 结论边界（明确不能从这里推出来的东西）

- **不能推出「所以 `i[a]` 是好写法」。** 它合法、等价、汇编相同，但没人那么写——
  这一期用它是为了证明**两边对称**，不是为了推荐它。
- **不能推出「C 没有类型检查」。** 反过来：`E1[E2]` 这个运算符**恰恰要求**
  一侧是指针、一侧是整数。`int *bad = arr[2];` 会被 gcc 明确警告
  （原文见 `docs/measured.md` 的 `DIAG:` 行）。
- **不能推出「这套数字跨编译器普遍成立」。** 反汇编是本机 `gcc 4.9.4 -O2 -m32` 的产物。
  别的编译器、别的优化级别、别的目标架构会生成不同的指令。
  **但"两条路径生成相同指令"这个结论对任何正确实现的编译器都成立** ——
  因为它们本来就是同一个表达式。
